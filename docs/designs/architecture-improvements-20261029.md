## FeatureRange: цель и текущая система

Пирогорск проверяет спрос перед запуском. Сохранённая анонимная заявка означает интерес к предварительной подборке; она не подтверждает заказ, оплату или доставку. Архитектурная цель этого спринта — сделать выпуск и проверку этой воронки воспроизводимыми. Рост трафика и индексации оценивается отдельно по поисковым системам и Метрике.

### Компоненты и границы

```mermaid
flowchart LR
  Data["Каталог, статьи, SEO-реестр"] --> Astro["Astro: статическая сборка"]
  Astro --> Pages["GitHub Pages: HTML, CSS, JS, изображения"]
  Pages --> Browser["Браузер: подборка и калькуляторы"]
  Browser -->|"POST /api/interest, UUID"| Worker["Cloudflare Worker: проверка, цены, лимит"]
  Worker --> D1["D1: interests и временные submission_tokens"]
  Worker -->|"saved + тот же UUID"| Browser
  Browser -->|"события из allowlist"| Metrica["Яндекс Метрика"]
  Data --> Worker
```

1. [astro.config.mjs](../../astro.config.mjs) задаёт `output: static`, `site/`, постоянные URL с завершающим `/`. GitHub Pages публикует готовые файлы; отдельный сервер для статей не требуется.
2. [src/data/catalog.ts](../../src/data/catalog.ts) — единый JSON-совместимый источник товаров, вариантов и предварительных цен. В текущем коде **14 товаров: 8 пирогов и 6 дополнений**, 24 варианта. [worker/src/catalog.ts](../../worker/src/catalog.ts) строит серверную проекцию из того же источника. Старое описание «13 товаров» в checkpoint Worker устарело; это не доказательство расхождения production.
3. [src/data/editorial.ts](../../src/data/editorial.ts), тематические модули и `seo-matrix.json` питают страницы, sitemap и перелинковку. [ContentLayout](../../src/layouts/ContentLayout.astro), [SeoHead](../../src/components/SeoHead.astro) и компоненты редакционных блоков уже переиспользуются. Канонический URL очищается от query/hash.
4. [storefront.ts](../../src/scripts/storefront.ts) обслуживает главную, проверяет восстановленную из localStorage подборку, принимает переходы из статей и калькулятора. [pie-planner.ts](../../src/lib/pie-planner.ts) отделяет расчёт и проверку сериализованной подборки от DOM. [EditorialInterest](../../src/components/EditorialInterest.astro) ведёт на главную; форма находится там.
5. [interest.ts](../../src/scripts/interest.ts) проверяет состав, удерживает UUID неизменённой попытки и показывает успех только после `ok`, `saved` и совпадения UUID. Потерянный ответ допускает повтор без дубля. [Worker](../../worker/src/index.ts) проверяет поля, Origin, размер тела, товары и даты; цену вычисляет сам, сохранение и допуск по лимиту выполняет D1 batch. Контактов в payload нет.
6. [analytics.ts](../../src/scripts/analytics.ts) пропускает только разрешённые цели/параметры, исключает QA/local-сессию и дедуплицирует `order_submit`. Ошибка Метрики не отменяет сохранение заявки.
7. [pages.yml](../../.github/workflows/pages.yml) проверяет типы, сборку, SEO, artwork и 24 Node-теста, затем публикует Pages и уведомляет IndexNow. Worker выпускается отдельным процессом, описанным в [worker/CHECKPOINT.md](../../worker/CHECKPOINT.md).

### Открытая гипотеза о скорости

[PERFORMANCE.md](../../PERFORMANCE.md) содержит публичный PSI главной от 27 октября: mobile 86, LCP 3871 мс; отдельный CLI давал 99 и 1705 мс. Причина render delay не доказана. Провести свежую диагностику неизменённой страницы и сохранить среду/URL/метрики; исправлять конкретную воспроизводимую причину, если она обнаружится. Локальный Lighthouse не подменяет публичный PSI; отсутствие воспроизведения не закрывает историческое отклонение.

### Выбор архитектуры

Сохранить Astro static + небольшой Worker + D1 и текущие предметные границы. React, SSR, CMS, очередь, кэш приложения и микросервисы не решают обнаруженные пробелы. Выделять `storefront.ts` в новые модули только при конкретном изменении поведения, которое требует общего контракта: размер файла сам по себе не оправдывает рефакторинг.

Для выпуска выбран проверяемый manifest и расширение существующего `/health`. Одна только общность исходников не проверяет развёрнутый Worker; новый сервис реестра выпусков был бы лишней инфраструктурой. Отпечаток покрывает ID, варианты и цены, а не редакционный контент. Проверка выполняется до и после публикации и фиксирует совместимость в эти моменты. GitHub concurrency сериализует Pages, но не ручной Cloudflare deploy: координатор выпуска завершает Worker rollout до Pages и повторно сверяет пару после публикации; проверка не является распределённой блокировкой. Если появятся параллельные операторы/автоматические Worker-релизы, их workflow должен использовать ту же concurrency group. Это также не гарантия одинаковых цен в давно открытой вкладке; цены до запуска предварительные. Строгая фиксация коммерческого предложения потребует отдельного контракта при переходе к реальным заказам.

Нынешние SEO-реестры частично пересекаются, но валидаторы уже сверяют итоговый HTML, sitemap и intent owner. Объединять все данные в универсальную схему сейчас не требуется. Свежесть адресов/цен и спрос остаются редакционной работой по seozavod; техническая глубина ссылок не доказывает спрос.

## Detailed Implementation Plan

### 1. Проверки перед выпуском — A1

- **Modify** [package.json](../../package.json), [package-lock.json](../../package-lock.json): добавить именованные команды Node/Worker/browser проверок; объявить `puppeteer-core` прямой devDependency с версией из действующего lockfile, сохраняя Node 24.
- **Modify** [pages.yml](../../.github/workflows/pages.yml): до upload/deploy запускать Worker verify, bundle, syntax check и браузерные проверки; использовать установленный Chrome либо явно подготовить Chrome на runner. При ошибке публикация не происходит. IndexNow остаётся после успешного deploy.
- Проверка: чистый `npm ci`, все существующие проверки и browser fixture. Ошибки пробрасываются ненулевым кодом; перехват внешней аналитики остаётся локальным.

### 2. Совместимость опубликованных частей — A2

- **Create** `src/data/catalog-contract.ts`: каноническая JSON-строка отсортированных `[id, [[value, price], ...]]`; сортировка по ID и строковому value, версия API `1`. Использовать только товары/варианты/цены из существующего каталога.
- **Modify** [worker/src/index.ts](../../worker/src/index.ts), [worker/scripts/bundle.mjs](../../worker/scripts/bundle.mjs): `/health` возвращает прежние поля и дополнительно `apiVersion: 1`, `catalogSha256` (SHA-256 канонической строки). D1 failure по-прежнему 503; CORS и POST v1 не меняются. Bundle должен включать тот же контракт без неизвестных импортов.
- **Create** `scripts/verify-release.mjs`: `manifest` записывает `site/release.json` после build с `apiVersion` и `catalogSha256`; `check` читает manifest и делает только GET к Worker `/health`, проверяет HTTP200, D1/intent и оба поля, иначе exit1 с понятной причиной. Из `interestEndpoint` строго с pathname `/api/interest` строится URL того же origin с pathname `/health`, без query/hash; неожиданный путь/протокол отклоняется. Тестовый API endpoint задаётся аргументом. Timeout 15 секунд; сетевой сбой завершает проверку ошибкой.
- **Modify** [pages.yml](../../.github/workflows/pages.yml): manifest включается в Pages artifact; проверка публичного Worker выполняется до upload/deploy и после deploy вместе с чтением опубликованного manifest (повторять чтение до 60 секунд из-за CDN, затем exit1). Изменение только контента проходит при том же отпечатке; изменение каталога требует сначала совместимого Worker. Ошибка после deploy означает уже опубликованный выпуск с неуспешной проверкой: IndexNow не запускается, координатор сверяет активную пару и восстанавливает предыдущую совместимую пару, затем повторяет проверку; бесконтрольного автоматического отката чужого нового Worker нет.
- **Modify** [worker/tests/interest.test.mjs](../../worker/tests/interest.test.mjs) и **Create** `scripts/release.test.mjs`: health fingerprint, изменение товара/цены, независимость от порядка, отказ 503/неверная версия/несовпадение/timeout. Ранее существовавший точный ответ POST сохраняется.
- Порядок первого выпуска: проверить локальную пару → выпустить Worker с текущим каталогом и новым health → независимо прочитать health → выпустить Pages → сравнить `release.json` и health. Если доступа к выпуску Worker нет, подготовленные изменения и точный блокер фиксируются; обход проверки недопустим, поскольку скроет именно проверяемую несовместимость.
- Откат: предыдущая совместимая пара исходников/артефактов; schema не меняется. При откате только контента с прежним каталогом Worker не требуется. При откате каталога вернуть соответствующий Worker и затем Pages; отметить возможную краткую несовместимость открытых вкладок. Повтор UUID и старый POST v1 поддерживаются.

### 3. Проверка готовых страниц — A4

- **Create** `worker/scripts/qa-site.mjs`: локальный HTTP server читает готовый `site/`; браузер обслуживает production origin перехватом запросов, Worker использует in-memory SQLite с действующей миграцией. Все внешние запросы перехватываются/отклоняются; реальные заявки и цели Метрики не отправляются.
- Проверить путь: статья `/journal/skolko-piroga-na-cheloveka/` → CTA в калькулятор/каталог → рассчитанная подборка → главная с тем же городом/составом → отправка формы → одна строка D1 и `order_submit` после подтверждения. Отдельно повторный переход с тем же URL не увеличивает подборку. Проверить 320 и 1280 px, отсутствие overflow и ошибок JS; неверная сериализованная подборка не должна становиться валидной заявкой.

## Приёмка и оставшиеся вопросы

1. Все прежние локальные проверки проходят; новая CI проверяет backend и готовый путь до deploy. Новые негативные проверки отличают несовместимый Worker от исправного.

4. Индексация, реальный спрос и стабильные публичные 100 остаются отдельными результатами; их нельзя вывести из успешной сборки.
