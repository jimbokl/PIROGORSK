# Проверка фактического выполнения Cron

24.10.2026. Worker `pirogorsk-interest`, опубликованная версия `c06b7ac1`, расписание `*/10 * * * *`. Обработчик удаляет из D1 `submission_tokens` только строки с `expires_at <= Date.now()`. Код и расписание не менялись во время проверки.

## Контрольный опыт

Через D1 Console в 14:41:15 UTC созданы два одноразовых служебных токена. Таблица `interests` не изменялась.

```sql
INSERT INTO submission_tokens(request_id,rate_key,window_start,slot,expires_at)
VALUES
('qa-cron-expired-20261024','qa-cron-expired',0,1,(unixepoch()-60)*1000),
('qa-cron-control-20261024','qa-cron-control',0,1,(unixepoch()+1800)*1000)
ON CONFLICT(request_id) DO NOTHING;
```

Независимое чтение:

```sql
SELECT request_id,datetime(expires_at/1000,'unixepoch') AS expiry_utc,
datetime('now') AS checked_utc
FROM submission_tokens WHERE request_id LIKE 'qa-cron-%';
```

| Время UTC | Результат |
| --- | --- |
| 14:45:44 | Обе строки присутствуют: expired до 14:40:15, control до 15:11:15 |
| 14:48:15 | Обе строки всё ещё присутствуют |
| 14:50:55 | Просроченной строки нет; действующий control сохранён |

Между чтениями не вызывались API заявок, ручной DELETE, Run Now или новый deploy Worker. Таким образом, плановый запуск 14:50 UTC выполнил очистку, сохранив непросроченный токен. Контрольный токен оставлен для естественного истечения и очередной очистки.

Доказательства: [до запуска](screenshots/cron-canary-before-20261024.jpg), [после запуска](screenshots/cron-canary-after-20261024.jpg). Cron Events при этом продолжал показывать пустую историю: [снимок](screenshots/cloudflare-cron-empty-20261024.jpg). Пустая таблица событий не использована как доказательство отсутствия выполнения.

В 14:51:28 UTC `SELECT COUNT(*), MAX(created_at) FROM interests` вернул **3 строки**, последнее создание `2026-10-24T11:05:15.791Z`: это три ранее задокументированных QA, исключённых из отчётов спроса в [ANALYTICS.md](../ANALYTICS.md). Новых заявок в этой проверке не создавали. Логи/трейсы/Issues остаются OFF.
