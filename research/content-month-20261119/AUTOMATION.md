# Ежедневный выпуск на Windows

Рабочая копия на этой машине — D:/Codex/PIROGORSK. У репозитория origin jimbokl/PIROGORSK и рабочая ветка main. Проект, зависимости, журнал, черновики и отчёты хранятся на D:. Перед началом сверить AGENTS.md, текущий раздел BUILD-STATE.md и BACKLOG.md.

## Выбор одного выпуска

1. Если D: или проект недоступен, сообщить о блокере и завершить запуск. Не переносить рабочую копию на системный диск. Для команды Node взять Node.js 24 с внешнего диска. При восстановлении он размещён в D:/Codex/PIROGORSK-recovery-2026-11-14/tools. Явно выставить PATH для npm и рабочий каталог для каждой команды. Для локальных проверок использовать существующие зависимости; при необходимости поставить пакетный кэш на D:.
2. Прочитать topic-map.json, BRIEFS.md и daily-publications.json, затем выполнить node scripts/editorial-slot.mjs с реальной датой. Команда с --at только читает очередь и служит для проверки календаря. Автоматизация стартует в 10:00 Europe/Kaliningrad. Перед подготовкой сверить дату и время этого пояса независимо от системного UTC.
3. При no-slot или done тихо завершить выполнение. После окончания окна плана один раз сообщить о потребности в следующей очереди. При prepare записать одну запись с date, topicId, slug, url, status: preparing, startedAt. При resume продолжить запись той же даты. При reconcile сначала проверить незавершённую запись прошлой даты и состояние Git, CI и живого URL. Завершить проверку уже отправленного выпуска или зафиксировать deferred для невыпущенного материала. За тот же запуск нельзя автоматически догонять старую и выпускать новую статью.
4. Журнал допускает статусы preparing, pushed, published и deferred. Переход в pushed требует точного SHA и URL выбранного запуска CI, как только он появится. Published требует успешного CI, подтверждения живого URL и протокола. Deferred требует конкретной причины и ссылки на рабочий материал. Для записи использовать один topicId на местную дату. Если у записи уже есть SHA, сначала сверить, отправлен ли он. При уже опубликованном SHA завершить проверку вместо повторного коммита или деплоя.

## Подготовка и выкладка

- Сверить текущий GitHub main и рабочую копию. Учитывать локальные коммиты этого спринта, не смешивать выпуск с чужими незакоммиченными изменениями. В один коммит публикации включать только относящиеся к слоту изменения и ранее проверенные задачи цикла. При конфликте или параллельном выпуске остановиться и описать препятствие. Не использовать force push.
- Для новых статей сверить владельца интента и отсутствие страницы в реестре и на сайте. Для обновления оставить текущий URL и дату первой публикации, заменить только содержательно улучшенные разделы и дату существенного обновления. Опираться на бриф, источники, alt, обложку и OG из очереди. Для CNT-101 использовать подготовленный черновик в drafts/CNT-101. Любой факт, меняющийся со временем, проверить до выпуска. При отсутствии существенного подтверждения отложить строку вместо публикации непроверенного текста.
- Новый материал добавляется в monthly-articles.json, monthly-article-meta.json, monthly-article-figures.json, article-artwork.json и seo-matrix.json по примеру research/content-daily-20261107/integrate.mjs. Путь к обложкам и диаграммам должен поддерживаться существующим import.meta.glob. Добавить контекстные переходы из связанных материалов. При обновлении выбрать соответствующий исходный реестр и сохранить связанные факты и элементы статьи. Сразу проверить, что разметка и локальный HTML используют правильный URL и дату.
- До push выполнить npm run check, npm run build, npm test, npm run test:worker, node scripts/verify-seo.mjs, node scripts/verify-seo-map.mjs и node scripts/verify-article-artwork.mjs. Дополнительно проверить новые страницы и таблицы на 320, 390 и 768 px в браузере и декодирование обложки и врезок. Для Windows при ограничении установленного Chrome использовать имеющийся Chromium headless shell для локальной браузерной проверки. Сохранить доказательства на D:.
- После проверок выполнить обычный push main и дождаться workflow Deploy Pages для точного SHA. Проверить HTTP 200, canonical, обновлённые текст и даты, наличие адреса в sitemap и журнале, обложку и переходы, результат IndexNow. Приём квитанции не равен индексации. При ошибке CI или несовпадении публичной версии сохранить этап, SHA, CI и ошибку, с которыми следующий запуск сможет продолжить. Не менять цены, заявки, CRM или настройки продажи в рамках редакционной задачи.
- Записать результат в daily-publications.json, BACKLOG.md и BUILD-STATE.md со ссылками. Коммит исключительно с протоколом после уже состоявшейся выкладки можно отметить [skip ci], чтобы не дублировать сборку. Уведомить пользователя о состоявшемся выпуске, существенном сбое или необходимости вмешательства. При повторе без изменений оставаться тихим.
